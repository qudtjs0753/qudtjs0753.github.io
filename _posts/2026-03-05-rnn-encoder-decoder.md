## 시퀀스란 무엇인가

시퀀스(Sequence)는 **순서가 있는 데이터의 나열**이다. 일반 데이터와의 차이는 **순서(order)가 의미를 가진다**는 점이다. 순서를 바꾸면 의미가 달라지거나 없어진다.

| 도메인 | 시퀀스 예시 |
|--------|------------|
| 자연어 | "나는 밥을 먹었다" - 각 단어가 순서대로 나열 |
| 시계열 | 주가 데이터 - 시간 순서대로 나열된 가격 |
| 음성 | 오디오 신호 - 시간에 따른 파형 샘플 |
| DNA | ATCGGA - 염기서열 순서 |
| 동영상 | 프레임이 시간 순서대로 나열 |

일반 신경망(MLP 등)은 입력을 독립적으로 처리한다. "나는 밥을 먹었다"에서 각 단어를 개별로 보면 문맥을 알 수 없다. RNN은 시퀀스를 **한 스텝씩 순서대로 처리하면서 이전 스텝의 정보를 기억(hidden state)**하기 때문에, 순서에 담긴 문맥을 활용할 수 있다.

## RNN의 세 가지 입출력 패턴

RNN에는 세 가지 주요 입출력 패턴이 있다. 이것들은 별도로 "발명"된 것이 아니라, **풀고자 하는 문제의 입출력 형태**에 맞춰 연결 방식을 달리한 것이다.

### Sequence-to-Vector (Many-to-One)

시퀀스를 순서대로 읽고, **마지막 hidden state 하나**만 출력으로 사용하는 방식이다.

가변 길이 텍스트/시계열을 받아서 **하나의 판단**을 내려야 하는 문제에 사용된다.

| 용도 | 예시 |
|------|------|
| 감성 분석 | "이 영화 정말 재밌다" -> 긍정 |
| 스팸 분류 | 이메일 전체 -> 스팸/정상 |

RNN 초기(1990년대)부터 자연스럽게 사용되었다. 분류 문제에 RNN을 적용하면 자연스럽게 이 형태가 된다.

### Vector-to-Sequence (One-to-Many)

하나의 벡터(고정 입력)를 초기 hidden state로 넣고, **스텝마다 출력을 생성**하는 방식이다.

하나의 입력으로부터 **순서가 있는 출력을 생성**해야 하는 문제에 사용된다.

| 용도 | 예시 |
|------|------|
| 이미지 캡셔닝 | CNN이 뽑은 이미지 벡터 -> "a dog running on the beach" |
| 음악 생성 | 시드 벡터 -> 음표 시퀀스 |

2015년 Vinyals et al.의 **Show and Tell** 논문에서 이미지 캡셔닝으로 주목받았다. CNN(이미지->벡터) + RNN(벡터->문장) 조합이다.

### Sequence-to-Sequence (Many-to-Many)

인코더 RNN이 입력 시퀀스를 벡터로 압축하고, 디코더 RNN이 그 벡터에서 출력 시퀀스를 생성하는 방식이다. 사실상 **Seq-to-Vec + Vec-to-Seq의 결합**이다.

입력도 시퀀스, 출력도 시퀀스인데 **길이가 다를 수 있는** 문제를 풀기 위해 등장했다. 기존 RNN은 입출력 길이가 같아야(매 스텝마다 1:1 대응) 했는데, 번역처럼 입출력 길이가 다른 문제를 풀 수 없었다.

| 용도 | 예시 |
|------|------|
| 기계 번역 | "나는 학생이다" -> "I am a student" |
| 요약 | 긴 문서 -> 짧은 요약문 |
| 챗봇 | 질문 문장 -> 답변 문장 |

2014년 Sutskever et al.의 **Sequence to Sequence Learning with Neural Networks** 논문에서 제안되었으며, 이후 Attention, Transformer로 이어지는 출발점이 되었다.

### 세 패턴 요약

```
RNN (1990년대~)
 |
 +-- Seq -> Vec : 시퀀스를 하나의 판단으로 (분류)
 |
 +-- Vec -> Seq : 하나의 입력에서 시퀀스 생성 (캡셔닝, 2015~)
 |
 +-- Seq -> Seq : 인코더-디코더, 가변길이 입출력 (번역, 2014~)
      +-- = Seq->Vec + Vec->Seq 결합
```

## 1:1 매핑 RNN vs 인코더-디코더: 왜 분리했을까

Seq-to-Seq에서 가장 중요한 질문은 "왜 단순한 1:1 매핑 RNN 대신 인코더-디코더 구조를 쓰는가"이다.

### 1:1 매핑 RNN (Naive Seq-to-Seq)

```
입력:  x1 -> x2 -> x3
       |      |      |
출력:  y1    y2    y3
```

매 타임스텝마다 입력 하나, 출력 하나. 입출력 길이가 **반드시 같아야** 한다.

### 인코더-디코더

```
인코더: x1 -> x2 -> x3 -> [context vector]
                                |
디코더:                    y1 -> y2 -> y3 -> y4
```

입력을 **전부 읽고 나서** 출력을 생성한다. 입출력 길이가 **달라도** 된다.

---

## 인코더-디코더가 더 나은 이유

### 1. 입력 전체를 본 뒤에 출력을 시작한다

1:1 매핑에서 y1을 생성할 때는 x1만 본 상태다. 하지만 번역에서는 문장 끝까지 봐야 의미를 알 수 있는 경우가 많다.

```
"나는 학생이 아니다" -> "I am not a student"

1:1 방식: "나는"만 보고 y1을 내야 함
인코더-디코더: 문장 전체를 읽은 뒤 생성 시작
```

"아니다"를 봐야 "not"을 넣을지 알 수 있는데, 1:1은 이미 앞부분 출력이 끝나버린다.

### 2. 입출력 길이가 독립적이다

| 입력 | 출력 |
|------|------|
| "나는 학생이다" (3토큰) | "I am a student" (4토큰) |
| "감사합니다" (1토큰) | "Thank you very much" (4토큰) |

1:1은 이런 상황 자체가 불가능하다. 인코더-디코더는 디코더가 EOS(종료 토큰)를 생성할 때까지 자유롭게 출력한다.

### 3. 인코더와 디코더가 각자의 역할에 집중한다

- **인코더**: 입력의 의미를 이해하고 압축하는 데 특화
- **디코더**: 출력을 생성하는 데 특화

1:1 RNN은 하나의 hidden state가 "이해"와 "생성"을 동시에 해야 한다.

## 인코더-디코더의 한계

### 병목(Bottleneck) 문제

입력 시퀀스가 아무리 길어도 **고정 크기 벡터 하나**로 압축해야 한다.

```
인코더: x1 -> x2 -> ... -> x1000 -> [고정 크기 벡터]
```

긴 문장일수록 정보가 손실된다. 이 문제를 해결하기 위해 **Attention 메커니즘**(2015, Bahdanau et al.)이 등장했다. 디코더가 매 스텝마다 인코더의 모든 hidden state를 참조할 수 있게 하여 병목을 완화했다.

### 속도

인코더가 입력을 끝까지 읽어야 디코더가 시작되므로, 1:1 대비 **지연(latency)**이 있다. 실시간 스트리밍 같은 경우에는 1:1 방식이 더 적합할 수 있다.

---

## 최종 비교

|  | 1:1 매핑 RNN | 인코더-디코더 |
|--|-------------|-------------|
| 입출력 길이 | 반드시 동일 | 자유 |
| 출력 시 문맥 | 현재 스텝까지만 | 입력 전체 |
| 역할 분리 | 없음 | 인코더/디코더 분리 |
| 병목 문제 | 없음 | 있음 (Attention으로 해결) |
| 지연 | 낮음 | 인코더 완료까지 대기 |

인코더-디코더가 더 나은 핵심 이유는 **"전체를 이해한 뒤 생성한다"**는 단순한 원리이며, 그 대가로 생긴 병목 문제는 Attention에서 Transformer로 이어지며 해결되었다.
